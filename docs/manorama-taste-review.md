# manorama taste review

Baseline implementation review · 1 November 2026

The main problem is not a lack of styling. Three generations of interface coexist: the newer shared owner screens, the web Library's oversized brand treatment, and macOS's older welcome/account layout. The improvement drive should consolidate those surfaces, remove repeated explanation, and protect the viewing experience. It should not introduce another design direction.

This replaces the previous 26-point prototype review. Findings below are based on the implementation, with recommendations distinguished from defects and with unsupported earlier claims withdrawn.

## Scope and evidence

- **Repository:** `thecont1/manorama`, branch `main`, commit `264af13f69c5ff8de74c3e2dfcfd84caa3a1d850` (“wordmark over Library's left edge, + Add Gallery pill, right-rail ad”). This is a fresh authenticated GitHub checkout, not the old sandbox excerpt or prototype. Unpushed work on the Mac is not included.
- **Web:** ran the current Vite app; inspected Welcome, Privacy, a locally seeded signed-in Library at 390×844 and 1440×900, its action menu, Gallery details and Settings. Test data and image routes were isolated from production.
- **iOS UI:** ran the actual `native/main.tsx` browser build and the repository's `.work/stocktake/parity-native.playwright.ts`. All four capture tests passed, producing fresh captures of Welcome, Library, Add, Details, Reorder, Settings, Visionary, Privacy, curtain, viewer, chrome, Display and Info at 390×844 and 375×812. These tests use synthetic photographs and mocked account responses; passing them is capture coverage, not a full product acceptance test.
- **macOS UI:** ran the current desktop Vite build with the repository's mocked Tauri bridge and existing sample photographs. Opened Library, card menu, local Gallery details and Publish/Share at 1280×840; also inspected `Catalogue.tsx`, `LocalGalleryDetails.tsx`, `ShareFlow.tsx` and desktop styles.
- **Device limit:** the Mac did not respond. Neither a real iOS WKWebView nor a packaged Tauri application was exercised. Native pickers, system share sheets, App Store sheets, safe areas, hardware keyboards and OS-level focus still need a device check. This is an implementation UI audit, not a claim that all native behaviours passed.
- **Historical captures:** repository screenshots helped locate surfaces, but fresh captures and current source take precedence. Several older screenshots no longer match the latest web header.

The captured frames committed to the repository live under `docs/redesign-parity/` — web captures in `web/`, native captures in `native/`. Application source was not edited.

## Direction to preserve

Keep Bricolage Grotesque, the quiet dark surfaces, warm ink, the colourful wordmark, and magenta reserved for progress and selection. Keep natural-aspect-ratio rails on Library and Gallery details, uniform-height Reorder thumbnails, single-photograph Content Credentials, and the in-app Privacy screen.

Do not change strip stepping, image-fit mathematics, uncropped photographs, vault policy, publication consent or ownership boundaries as a side effect of this work. The frosted curtain is explicitly approved: a generic skill rule against blur does not override that decision.

## Priority A: fix the visible drift first

### Library hierarchy and wasted space

- **A1 · Web Library has become a second landing page.** At 1440px the wordmark measures 560×187px; the Library title begins around y=303px. On the 390px capture, the first rail starts around y=349px. The shared logo is 140×47px, and the native Library reaches its photographs much sooner. Restore a compact owner header, with Library and Add on one row. Reserve the large wordmark for Welcome. The most recent commit intentionally introduced the larger wordmark, so treat this as a recommendation to reconcile that newer choice with the earlier consistency decision, not an accidental CSS bug. **Where:** `app/islands/Admin.tsx` (`admin-hero-brand`, `admin-add-pill`), `app/styles.css` (`admin-hero-brand`, `landing-brand-mark`, `admin-library-heading`). **Done when:** the gallery, not branding, is the first dominant object; mobile and desktop use one documented owner-header system.

- **A2 · The desktop ad column consumes space even without an ad.** The fresh web Library has no `.account-ad`, yet `.gallery-list` computes to `padding-right: 460px` at 1440px. The same broadly scoped selector also narrows the macOS catalogue, leaving a large empty right side. Make the two-column layout conditional on an actual sponsored placement and scope it to the surface that owns it. When present, the ad should remain secondary to the galleries; do not change the approved mobile ad position merely to solve desktop layout. **Where:** `app/styles.css`, the `@media (min-width: 900px)` rule for `.admin-page--selector .gallery-list`; `Admin.tsx` conditional ad rendering; `desktop/islands/Catalogue.tsx`. **Done when:** with ads disabled, absent or unavailable, the list recovers the reserved width; with an ad present, both columns fit without clipping.

- **A3 · macOS still opens with the old product pitch.** The current catalogue spends its upper area on a large logo, dictionary definition, “WOW-est” copy, public address, greeting, plan sentence, import explanation and sync state before “Your galleries.” The account drawer repeats much of it. Replace this with the compact Library shell: shared mark, Library, Add, Settings, and a quiet local/cloud scope or sync status where needed. Preserve local-only operation and folder import; move their explanation to the relevant action. **Where:** `desktop/islands/Catalogue.tsx`, especially the account drawer and `admin-overview`; inherited `admin-*` styles. **Done when:** returning users encounter their photographs first, and the pitch does not appear twice.

### Typography and wording

- **A4 · The shared design tokens are not reaching all owner screens.** Runtime measurement shows the web Library title, Add control and gallery title using Manrope, while newer `.m-owner` screens use Bricolage. macOS retains legacy font assignments; Privacy mixes Bricolage headings, Playfair body text and a tracked DM Mono date. Apply the shared owner typography deliberately to each shell, then remove superseded selectors after checking their consumers. Do not merely delete every old font declaration: code and keyboard keys can legitimately use monospace, and unrelated operator screens need their own review. **Where:** `app/styles.css`, `native/styles.css`, `desktop/styles.css`, `Admin.tsx`, `Catalogue.tsx`, `app/components/PrivacyPolicy.tsx`. **Done when:** Library → Details → Settings → Privacy reads as one product, in both supported themes.

- **A5 · Welcome has reverted to the old headline and long explanation.** Both current public and native Welcome use “the WOW-est way…” rather than the approved quiet introduction. The native inspector reports a three-line headline at 1440, 768 and 390px, with a 48px desktop title. Restore the approved “Your shared folders, shown properly.” or agree one equally concise replacement, followed by one factual sentence. Keep the no-photographs-before-sign-in rule and accessible provider buttons. Do not add decorative content to fill intentional space. **Where:** `app/components/PublicWelcome.tsx`, `native/islands/Welcome.tsx`, Welcome styles. **Done when:** web and native use the same approved copy, and sign-in is the obvious next step.

### Details, Reorder and the plan

- **A6 · macOS local Details omits the approved rail header.** `LocalGalleryDetails.tsx` shows the gallery name in the top bar and again in the body, disables the logo, and has no scrolling image strip. Bring its header into the same family as Library and cloud-gallery Details: shared mark, natural-ratio rail, title and concise source metadata. Keep local capabilities distinct; do not add cloud-only storage switches just for visual parity. **Where:** `desktop/islands/LocalGalleryDetails.tsx`, `app/components/GalleryDetailsView.tsx`, Library rail components. **Done when:** the same gallery is recognisable when moving from its Library card to Details, with no duplicated title bar.

- **A7 · Reorder restores an explicitly removed status message.** `GalleryEditor.tsx` writes “Moved … to position …” into the visible `.native-editor-note`, which is also the live region. It also titles the bar `Reorder ${title}`. Separate screen-reader announcements from visible instructions; retain the initial instruction and useful picked-up state, then announce moves invisibly. Use “Reorder” in the bar. Preserve error and save feedback. **Where:** `native/islands/GalleryEditor.tsx`, `native/styles.css`, and tests that currently assert the visible moved message. **Done when:** moving a photograph does not replace the visible instruction with a transaction log, while assistive technology still hears the result.

- **A8 · Visionary still presents prototype benefit copy as product information.** The current `Paywall.tsx` hard-codes “256 MB → larger” and “Kept, not for 30 days,” alongside “3 → 99.” Replace vague wording with the actual billing/storage/retention rules and derive numbers from shared policy where possible. If no fixed storage allowance exists, describe the real rule rather than inventing one. Keep Restore, Manage subscription and required legal access; those are functional requirements, not clutter to delete. **Where:** `native/islands/Paywall.tsx`, billing and vault policy modules. **Done when:** every benefit is specific, verifiable and understandable without the handoff document.

## Priority B: make the interactions and small surfaces coherent

- **B1 · Protect photographs from temporary chrome as well as arrows.** The implementation gives arrows reserved space, but `ViewerChrome.tsx` and `.m-chrome` still position the temporary top and bottom controls over the stage. This remains in tension with “photographs are sacred.” Prefer the existing non-image control region, with a deliberate reveal-state layout if more room is needed. Do not introduce an image resize on every idle-timer tick or alter strip docking. **Where:** `app/components/viewer/ViewerChrome.tsx`, `app/islands/Viewer.tsx`, `.m-chrome*` rules. **Acceptance:** no control covers a photograph in supported modes; opening or hiding controls preserves the current photograph and scroll target. This geometry decision needs a small reviewed interaction prototype before implementation.

- **B2 · Distinguish publication from sharing on macOS.** The row says “Publish/Share,” then opens a sheet titled Share with Dropbox and Google Drive destinations. For a local-only gallery this means uploading originals to create a public link, not merely distributing an existing link. Use Publish for that action and Share link after publication. State the destination and consequence before consent; keep normal link sharing on the system share path. In the audit build both providers were “Not configured in this build”; treat that as a development state, not a production outage. **Where:** `LocalGalleryDetails.tsx`, `Catalogue.tsx`, `ShareFlow.tsx`. **Acceptance:** the label tells users whether they are uploading files or sending a URL.

- **B3 · Reduce repetition in Details without removing useful context.** Shared Details repeats the title in Name and the path in Share link; the caption is repeated in its edit row. First remove the Share link path preview because the full address is already visible. Keep Name/Caption values only if they help editing; avoid reproducing a long caption when the full text is immediately above. Do not impose an arbitrary “a name may appear only twice” rule. **Where:** `app/components/GalleryDetailsView.tsx`. **Acceptance:** each row communicates an action or a meaningful state, not a second copy of the header.

- **B4 · Tighten the Library metadata stack.** The native capture has a noticeable gap between count/source and caption, then another before the next gallery. Audit the complete computed cascade, not just the later “caption 6px” rule: retain a compact title → metadata → caption group and reserve the larger gap for the next gallery. Keep the rail's uncropped proportions and full-bleed treatment. **Where:** `.lib-card`, `.lib-card-sub`, `.native-gallery-caption`, inherited paragraph/list rules. **Acceptance:** cards with no caption, one line and several lines all have deliberate grouping; no CSS minimum height creates a false empty paragraph.

- **B5 · Use a Settings glyph for Settings.** The native Library's button is labelled Settings but draws a sun-like circle with rays; the web screen uses a recognisable gear. Use the shared gear, leaving appearance controls inside Settings. **Where:** `native/islands/GalleryList.tsx`, the `TopBar` end slot. **Acceptance:** the visual meaning and accessible name agree across platforms.

- **B6 · Make Display explanations shorter, not absent.** Current Canvas choices include Blank, Dark and Light; a long hint explains that Blank means photographs line up against one another. That distinction is not self-evident, so retain concise help instead of deleting all descriptors. Put it below the control when narrow, rather than squeezing it beside the label. Keyboard shortcuts should remain available only when appropriate to the input device. The phone-size capture used a fine pointer, so its shortcuts list is not evidence of an iPhone bug. **Where:** `app/components/viewer/DisplaySheet.tsx`, sheet hint styling. **Acceptance:** no hint competes with its control or wraps awkwardly at 375px and enlarged text; test actual touch and fine-pointer contexts separately.

- **B7 · Make Privacy a reading screen within the same app.** Keep the shared legal content unchanged, but remove the ornamental typographic change and excessive nested-card treatment. Use the app body face, a readable line length, consistent heading spacing, and the originating screen's back navigation. Print can remain a desktop utility rather than a prominent phone action. **Where:** `app/components/PrivacyPolicy.tsx`, `.policy-document*` styles, native Privacy wrapper. **Acceptance:** the legal text is intact and the screen no longer feels like a different website.

- **B8 · Finish control sizing and copy consistency.** The web Add Gallery control measured 37px high in the desktop capture, and native Reorder explicitly overrides Cancel/Save to a 36px minimum. Compact desktop visuals can be acceptable, but touch hit areas must meet the agreed 44px floor. Standardise Add versus Add Gallery, Library versus Your galleries, and the rescan row — “Refresh gallery contents” on every surface — unless a platform-specific meaning genuinely differs. Keep one-word viewer controls; do not force the same restriction onto legal text and explanatory forms. **Where:** shared buttons, `admin-add-pill`, `native-editor-cancel/save`, `Catalogue.tsx`, `LocalGalleryDetails.tsx`. **Acceptance:** measured touch targets pass at phone sizes and enlarged text; labels refer to the same job consistently.

## Corrections to the previous review

The earlier review judged the prototype and overreached in several places. These should not become implementation tickets:

- **No vertical centring of Reorder:** top-aligned photographs and unused space in a short gallery are appropriate for an editor. Filling space is not the goal.
- **No claimed floating-slider defect:** the implemented sizer is a non-shrinking flex sibling after the scroll region. The old overlap allegation is not established.
- **No automatic icon requirement for Share:** text-only options are legitimate and often quieter. Consistency of behaviour and wording matters more than adding icons to every list.
- **No current address-contrast failure established:** `.d-addr` now uses `--m-meta`, defined as `#98948c` in the dark theme. The old screenshot-based failure claim is withdrawn; measure each actual foreground/background pair before filing a contrast bug.
- **Do not remove the approved curtain blur or gradient solely because a generic rule dislikes it:** preserve legibility and the requested dissolve. An aesthetic preference is not evidence of a regression.
- **No blanket removal of repeated position information:** “Photograph 1 of 8” usefully identifies the Info dialog independently of a dimmed background counter.
- **No unverified end-card defect carried forward:** the current viewer has role-aware Library exits. End-card chrome and keyboard focus need a targeted current-state test before deciding what to remove.
- **No arbitrary ban on bright selected segments:** the approved cream selection is meaningful. Change it only if a real screen has competing emphasis, not because a sheet contains several selected values.
- **Do not infer image-loading bugs from fixture captures:** native parity images are synthetic SVGs; the web seed and desktop bridge use test routes. A blank fixture cell is not evidence that production photographs fail.
- **Info versus Details:** this remains a possible usability refinement, not a verified defect. Keep the approved names for this drive unless a brief user test shows confusion.

## Check results and remaining coverage

The native capture suite passed four tests across the two phone widths. Separately, the taste inspector on the actual native Welcome reported **3 failures and 3 warnings**: headline wrapping at three widths, plus cream-colour, desktop empty-space and oversized-title warnings. Those results apply to Welcome only, not to the whole app. The cream ink remains a deliberate exception; the title and hierarchy concerns support A5.

The public web routes, signed-in owner surfaces and mocked macOS UI were opened and captured, but no claim is made that the full repository acceptance suite passed. Light-mode styling, long real albums, verified C2PA manifests, video/fold layouts, slow/offline recovery and native system UI need targeted follow-up checks rather than speculative taste findings.

## Recommended execution order

- **Pass one: shared shell and scope.** A1–A4 and A6. Establish one owner-screen family; eliminate the unconditional ad-column reservation and macOS pitch. Compare Library, Details and Settings side by side before adding any more styling.
- **Pass two: copy and editing.** A5, A7, A8, B2, B3 and B8. Restore approved copy, remove the move log, make plan claims factual and publication consent unmistakable.
- **Pass three: interaction polish.** B1 and B4–B7. Review chrome geometry separately from image physics; tune spacing, settings affordances, Display hints and Privacy.
- **Release gate:** compare web at 390/1440/2560px, native UI at 375/390px, and macOS at its minimum supported window and 1280/1440px. Include empty and populated libraries, ads absent/present, long names/captions, light/dark owner themes, touch/keyboard, reduced motion and real-device safe areas. Keep the approved strip, image-fit and single-image credentials tests green.

No application changes, commits or deployments were made during this review. The Mac repository was not updated because the device was unavailable; the revised review is delivered as a document.
