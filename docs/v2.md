## 1. Sign-in flow

```
GET / ────────────────────► the landing page: brand, one quiet button
   │  click "Continue with Dropbox"
   ▼
GET /auth/dropbox ──────► mint CSRF state, set 10-min cookie, 302 →
   │                       dropbox.com/oauth2/authorize?client_id=…&state=…
   │                       (Dropbox shows consent; creates account if needed)
   ▼
GET /auth/dropbox/callback?code=…&state=…
   │  verify state cookie matches        ← app/lib/dropbox-oauth.ts
   │  exchange code → access token       (no token is kept)
   │  get_current_account → account_id, name, verified email
   │  upsert user in D1 (mint owner slug on first sign-in)
   │  sign HS256 session JWT, set httpOnly cookie
   ▼
302 → /<owner_slug>   (the dashboard)
```

## 2. The session

`@/Users/home/DEV/tools/manorama/app/lib/dropbox-session.ts` — the cookie carries **only** the Dropbox account ID, signed with `HOST_API_JWT_SECRET`. Everything else (owner slug, name, tier) is loaded from D1 on every request — so a slug change applies instantly, no cookie re-issue. Fail-closed everywhere: missing secret, bad cookie, deleted account → `null` → 401 JSON (API) or `/` redirect (dashboard).

## 3. Data model (D1)

```sql
users     (dropbox_account_id PK, owner_slug UNIQUE, display_name, email, tier)
galleries (owner_id + slug PK, title, caption, date, source_url, images_json)
```

The gallery slug is unique **per user**, not globally — `/mahesh/italy-2018` and `/sarah/italy-2018` can coexist. Galleries reference the immutable account ID, so changing your URL never orphans them. Without the D1 binding (dev/tests) an in-memory store takes over. `@/Users/home/DEV/tools/manorama/app/lib/user-repository.ts`, `@/Users/home/DEV/tools/manorama/app/lib/gallery-repository.ts`

## 5. The two rules you asked for

**Owner URL change** — the dashboard header shows `/<owner>` as a quiet pencil-editable control; while editing, the note *"Your gallery links will change with it."* sits under the field. ## 6. Vendo (the assistant)

`vendo/server.ts` uses the same `resolveManoramaSession` — a request without a valid session gets a null principal and Vendo refuses it. Its tools operate on the same owner-scoped API, and the guard policy (venue rules before risk rules, from the earlier fix) still governs every call.
